# M20 Pro 实机部署复盘：问题、修复与工程经验

复盘区间：2026 年 10 月 7—20 日；核心实机记录集中在 10 月 14—20 日。结论截至 2026 年 10 月 20 日。

本次工作将学生策略接入 M20 Pro 的真实感知与控制链路，涉及双板通信、CPU 高程估计、历史观测拼接、ARM 推理、SDK 接管、现场运动测试和故障诊断。最重要的经验是：实机效果由整条链路共同决定，训练成绩或模型加载成功都不能替代运行时验证。

截至复盘时，已完成多轮软件部署、若干部署缺陷修复和短距离运动验证；位姿跳变、阶高提示闪断、提前抬腿、过温根因及长期稳定性仍有待验证或解决。最新 20000 轮模型完成了软件部署与 SDK 初始化，尚无该权重实机行走和楼梯验收结论。

本文是历史工程复盘，不是当前机器的启动说明。文中的测量值只描述对应试验窗口，不作为现行配置参数；实际配置应以目标版本的参数台账为准。原始证据保存在部署工程，本仓库仅收录经过整理的复盘，来源定位见文末。

## 1. 系统边界与阶段进展

最终采用的主要数据链如下：

```text
原厂雷达数据链
    → GOS 原厂驱动
    → GOS 本机原生 DDS 读取
    ├─ 完整点云与 IMU → LIO → 机体位姿
    └─ 高程支路点云 → CPU 地形估计 → 高度、有效性、置信度
                                           ↓ 小型地形观测回传
AOS 关节与 IMU → 本体观测及历史 → 学生策略 → 动作映射 → SDK 下发
                                 ↑
                           手柄命令与状态机
```

v1 及本次相关后续学生的输入布局为：

```text
当前本体 57 + 高度 187 + 有效性 187 + 置信度 187 + 历史本体 171 = 789
```

“总维度相同”不足以保证兼容，排列顺序、缩放、历史更新时间及上一动作语义也必须一致。后续 v3.5 还需要配套的外部航向反馈；仅替换权重文件不能完成适配。

## 2. 主要问题与处理结果

### 2.1 大点云传输不完整与延迟

**现象。** 初始方案从 AOS 再转发大点云到 GOS，出现完整帧缺失和时效不足，板间百兆链路也限制了该路径。GOS 授时另有硬件发送时间戳等待超时，导致 PTP 反复掉同步。

**定位与修复。** 核对原厂驱动和已运行方案后，确认 GOS 已能接收并融合雷达数据。改为从 GOS 本机原厂驱动通过原生 DDS 取云，再经本机接口接入感知处理，AOS 只接收小型地形观测。旧 TCP/压缩转发候选退出正式链路。PTP 故障另行调整等待参数并重启验证。

**验证与边界。** 原生输入探针约 10 秒收到 96 帧，末点到回调收件的点龄平均约 22.26 ms；授时修复后连续 120 秒保持同步，最大偏差约 10 微秒。这分别证明对应输入阶段和授时窗口可用，不能替代整个感知—控制链的动态验收。当时授时使用临时配置，整板重启后需重新检查。[E1、E2]

**经验。** 先确认数据在哪里产生、已经经过哪些处理，再决定是否增加转发。架构上少一次大数据搬运，通常比继续优化冗余转发更有价值。

### 2.2 进入策略后支撑不足、前进数秒趴下

**现象。** 现场反馈前进约三秒后趴下，最初怀疑模型或手柄频率。

**已证实的部署缺陷。**

1. 成功推理后，腿部位置目标被反复限制在当前实测角度附近。测量不动时，目标也无法继续接近策略请求。
2. 地形拒绝后的 HOLD 每周期重新采用实测位置作为目标，身体下沉时保持目标随之下沉。
3. HOLD 清空历史，并将经过物理限幅的目标反算成上一动作，改变了训练输入语义。

离线执行实际控制代码的反例显示：一个应产生约 20 N·m 比例项的目标，被压缩为约 4 N·m。这是给定测量下的 PD 比例项分析，不是对真实总电机力矩的测量。

**修复过程。** 首先将目标推进基准改为上一条指令；HOLD 锁存支撑目标和增益、停止轮速；恢复归一化请求动作作为 `last_action`，仅在新一轮接管时初始化历史。后续按 MuJoCo 基准取消额外腿位置和轮速目标裁剪，保留对应的归一化动作处理。

**验证与边界。** 实机短时接管记录确认：目标不再受旧测量中心限幅束缚；进入 HOLD 后保持最后策略目标，轮速归零；动作历史与上一帧请求一致。但接管随后仍受地形超龄影响。由于原倒地瞬间缺少完整同步记录，不能认定某一个缺陷是唯一原因。[E3、E5]

**经验。** 部署适配必须复现训练中的控制语义。额外限幅、历史清零或“保持当前位置”都会改变闭环，不能仅因名称像保护措施就认为它一定合理。

### 2.3 手柄命令到达，但机器人没有响应

**现象。** 现场推动摇杆后没有预期动作，一度怀疑手柄发送频率和机器人接收频率不一致。

**定位。** 一次记录中已有 350 个周期包含非零摇杆命令，但策略在接管约 0.38 秒后因地形超龄进入锁存 HOLD。命令已经到达 SDK，控制状态没有允许继续执行策略。另一次 L1 无动作则来自手柄重连锁，操作步骤遗漏了重新使能。

**修复过程。** 补全与实际状态机一致的操作说明；对地形链拆分点云处理、位姿接收与发布回调，调整队列和 CPU 放置，修正耗时工作后仍使用旧时间检查、消费年龄重复累计等问题。后续也调整过准入预算，并在部分试验中授权使用全未知地形继续推理。

**验证与边界。** “摇杆没有到达”这一解释被日志否定；时效问题经历多轮修改，不能将一次静态通过描述成从此不再发生 HOLD。允许未知地形继续推理属于降级运行，不等于恢复了有效视觉预瞄。[E3、E4]

**经验。** 排障应沿“命令接收—状态机—策略推理—目标生成—实际下发”逐段检查。手柄心跳、摇杆包、控制周期和雷达更新属于不同事件，不要求所有频率相等。

### 2.4 静止能看到楼梯，移动中模型却收到未知地形

**现象。** 静态木阶重放的几何基本合理，实际运动却经常缺少预瞄信息。早期记录中，1270 个前进周期有 994 个整图未知；另一段移动记录中，133 个前进周期有 122 个整图未知。原始点云能看到阶状几何，不能证明模型在相应时刻收到了它。

**定位与修复。**

- LIO 层修复 IMU 历史积分、真实扫描结束时刻、去畸变端点及回调发布顺序。最终使用双线程加锁方案；单线程候选虽改善重入问题，却恶化现场时效，已撤回。
- 地形支路按前方扇形选择原始点，保留扇形内全部 point record，并调整云时效预算和 CPU 放置。原生接口仍交付完整扫描，LIO 分支仍使用完整云。
- 趴姿主要看见立面、踏面支持不足的情况单独处理，没有把未知区域填成平地来提高覆盖率。

**验证与边界。** 最终短距前进记录中，729 个已记录前进输入全部包含有效地形，其中 625 个具有约一级木阶的高度提示。原始采集交集内还核对了连续位姿移动及实际 SDK 输入、动作和下发关联。

这些结果不代表所有格点有效，也不代表每周期都能看见台阶。阶高提示仍出现最长约 0.90 秒的连续缺口。新旧试验并非完全匹配的轨迹，且扇形方案的关键路径中位耗时并未整体下降，不能把全部改善归因于“点更少、计算更快”。[E5、E6、E7]

**经验。** 静态几何、动态感知和策略利用感知是三个独立验收层。最终应检查模型消费时刻的真实输入，而不是只检查可视化地图。

### 2.5 周期 HOLD 与地图会话 HOLD 被同一种现象掩盖

**现象。** 策略多次停止，但不同试验的首个触发原因并不相同。

**周期问题。** 10 月 19 日记录到相邻周期约为 26.34 ms 和 13.64 ms，两者合计接近两个标称周期，表现为延后后赶回节拍。先只放宽上界，随后又撞下界。最终调整允许区间，并确认新二进制已加载。

这次修改只处理周期判定范围，没有改变调度器或计时位置，不构成不规则周期下长期闭环稳定性的证明。

**会话问题。** 后续两板日志确认：LIO 位姿变化超过连续性检查允许范围，GOS 重置地图会话，AOS 随后触发 `terrain source session changed`。v3.5 model5500 试验同样出现这条链路。位姿跳变的具体原因截至复盘仍未确定，重启和换权重不能算根因修复。[E8、E10]

**经验。** 每次先查第一条故障，再沿同一时间窗追溯上游。HOLD 后不断增长的计时、后续越界或其他连带症状，不能倒过来当作首因。

### 2.6 本机数值对拍通过，ARM 上仍有差异

**现象。** 学生模型的 Torch 与 ONNX 输出在既有容差下出现超差。部分本机修法在 ARM 上不能完整通过。

**定位与修复。** 逐层比较将一类误差定位到不同 CPU 实现的 FP32 累加路径。仅关闭预打包仍不足以通过 ARM 固定样本，最终 v3.5 导出采用：原 FP32 参数精确扩宽，线性层以 FP64 计算，线性结果回到 FP32 后执行原 ELU，外部输入输出仍为 FP32。

另一类 ARM 差异来自融合乘加造成的浮点边界变化，使航向反馈的邻接判定不同，改为与训练等价的离散列索引判断。

**验证与边界。** 实际 ARM 上固定 160 帧与历史 8587 帧合计 8747 帧通过原容差检查，航向场景另行验证。扩大极值域后仍存在相对训练 FP32 舍入结果的超差，未宣称全域等价。历史观测回放验证的是推理后端一致性，不是新策略在当时已经完成实机控制。[E9]

**经验。** 目标硬件是验收环境的一部分。应固定反例、逐层定位，并检查物理目标误差；不能只换一批随机样本或放宽容差来消除失败记录。

### 2.7 软件已经复制，但运行身份和日志仍可能失配

**现象。** LIO 不同版本可能具有相同的节点文件而加载不同动态库；源码修改后也曾出现增量构建未生效。详细日志达到容量上限后，某次 HOLD 的触发周期缺档。后续部署还遇到板端可用空间不足、重启后旧现场确认记录失效等问题。

**修复过程。** 校验实际进程入口及加载库，完整重编译并核对成品身份；新模型使用独立 release，保留原程序及原 `current`。根据磁盘余量设置日志预算，增加有限容量的控制台与关键事件记录。20000 轮版本显式复用已校验的安装依赖，记录该依赖不得随旧目录清理。

**验证与边界。** 最新部署记录核对了模型、二进制、进程环境和感知数据源，完成 SDK 初始化。详细日志未保存的历史周期仍然缺失，不能由后续日志补造。新版本实机行走和楼梯表现尚未验收。[E6、E10、E11]

**经验。** “改了代码”“构建成功”“文件在板上”“运行进程加载了它”需要分别核实。版本、依赖、回退和日志容量应与算法一起交付。

### 2.8 连接故障与过温需要单独归因

一次 SSH 故障中，网络已经连通，但本机 SSH agent 连续尝试多把密钥，耗尽服务端认证次数。改用明确的认证方式后，两板登录成功。这个案例说明：网络不可达、认证失败和服务异常需要区分，不能因 SSH 失败就继续修改路由。

另一次策略运行约 55 秒后，右后侧摆电机出现约 100°C 的过温记录并触发保护退出。现场趴稳后停止 SDK、保留日志并降温，但温升根因尚未确定。降温解决的是当时状态，不等于修复热问题。[E5]

## 4. 可复用的部署方法

### 先冻结输入、版本和判据

一次试验至少记录模型与配置哈希、部署代码和成品版本、实际进程、外参来源、启动时间、场景、姿态和负载。将“模型是否有效”和“部署是否忠实实现模型”作为不同问题验证。

对失败反例保留原输入和原门槛；修改后重新执行同一反例，同时保留正常对照。涉及不同姿态、轨迹、负载或模型的结果，应说明差异，不能拼成单因素改进结论。

### 依次通过五层验证

1. **契约与离线回放：** 观测、历史、动作、关节映射和异常分支符合参考实现。
2. **目标硬件：** 在 ARM 上验证数值、依赖、计算耗时和资源预算。
3. **真实感知：** 分别检查静态几何、运动时更新和模型消费时刻的有效性。
4. **短时接管：** 核对状态转换、实际推理、目标下发和退出行为。
5. **任务表现：** 统计完整成功与失败次数，检查提前抬腿、稳定性、温升及重复运行。

每层只支持自己的结论；话题有数据不能替代有效观测，DDS 发布返回不能替代电机执行确认。

### 在试验前设计记录

为每次试验设置独立编号，同步保存原始观测、策略动作、最终目标、本体状态、地形年龄、状态机和首个故障原因。需要评价动作时，加上带时间关联的视频及接触事件。明确日志容量、丢弃计数和停止记录的时刻。

每次现场结束立即标记结果与现象。此前“做了五六次，成功一次”缺少逐次对应关系，限制了成功与失败的对照分析。

### 区分修复、缓解和待查

- **修复：** 已定位的缺陷被改正，同一反例和正常对照均验证。
- **缓解：** 放宽门槛、降低负载或降级输入让当前运行继续，但原风险尚未完全消除。
- **待查：** 已找到触发链，根因或最终行为仍缺证据。

现场资源冲突时，封存当前状态并完成离线分析；重新测试前确认资源窗口。共享机器上的绑核、观察程序和日志写入本身也可能改变被测系统。
